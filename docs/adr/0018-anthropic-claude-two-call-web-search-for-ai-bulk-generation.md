# AI Bulk Generation calls Anthropic's Claude API, in two calls, not one

For #158 (part of the AI Bulk Generation map, #157), the server endpoint behind AI Bulk Generation calls **Anthropic's Claude API** (model `claude-sonnet-5`, configurable via `Anthropic:Model`) through the official `Anthropic` .NET SDK, using the `web_search_20260318` server tool capped at `max_uses: 8`. We considered OpenAI's equivalent (`web_search` tool + `text.format` json_schema on the Responses API, official `OpenAI` SDK) — cost and SDK maturity are near-identical between the two, but Anthropic's docs explicitly state structured output and tool use (including server tools like web search) are "independent and complementary" in a single request, while OpenAI's guides never address that combination and developer-community reports describe truncated/invalid JSON specifically when web search and structured output are combined on longer outputs — exactly the failure mode a full curriculum's lesson list is exposed to. Full comparison and cost estimate: [research artifact](https://github.com/ADCogburn/prokope/blob/research/ai-provider-web-search-generation/docs/research/ai-provider-web-search-generation.md).

Even though Anthropic supports combining web search and structured output in one request, the endpoint still makes **two separate calls**: Call 1 sends the curriculum name with the `web_search` tool (no `output_config.format`) and lets Claude produce free-text notes with citations; Call 2 is a plain request (no tool use) that feeds Call 1's notes back in and extracts them into the final lesson-list JSON via `output_config.format`. This splits "did we find the right content" (degrades gracefully if truncated, cheap to re-run without repeating paid searches) from "shape it correctly" (deterministic, no agentic-loop variability, cheap to retry on schema failure). Call 1 is prompted to say plainly when it can't find real source material for the typed curriculum name; that short-circuits the request before Call 2 runs, returning a distinct "not found" response rather than letting Call 2 fabricate a schema-valid but hallucinated lesson list. If Call 2 fails schema validation, the endpoint retries it exactly once — re-feeding Call 1's existing notes, no re-search — before failing the request.

The real API key is not committed: `Anthropic:ApiKey` follows this repo's existing secret pattern in production (empty placeholder in `appsettings.json`, real value via Railway's `Anthropic__ApiKey` env var), but locally it's supplied through `dotnet user-secrets` — the first use of that mechanism in this repo, and a deliberate departure from the Jwt/Google pattern of a working placeholder value in `appsettings.Development.json`. That file is committed to git, so a real external API key can never live there, unlike `Jwt:SigningKey`, where a fake local value works fine because signing and verification both happen locally against the same fake key.
